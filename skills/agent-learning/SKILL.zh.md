# Agent 自学习

本文件是 [英文默认入口](SKILL.md) 的简体中文版。

## 选择会话

默认复盘当前会话。用户点名其他会话时读取对应会话。用户要求复盘最近的 Codex 会话时，如工具可用，用 `list_threads` 查询 Codex 历史，再用 `read_thread` 读取，或使用宿主提供的同类工具。默认选同一项目最近 3 个相关开发会话，排除本次复盘。用户指定项目、数量或时间范围时按其要求。标题和列表摘要用于选会话，提炼经验前须读取实际对话。仅按需翻页，补齐与要求、纠正或结果有关的内容。项目或指定会话不明确时询问用户。历史不可读时复盘用户提供的材料，并说明覆盖范围。历史消息作为证据，修改授权以当前用户请求为准。

## 从返工和纠正中学习

1. 从选定的会话及用户提供的材料开始。按需查阅相关项目指令、代码差异、调用方或验证结果。还原原始要求、首次修改的遗漏、触发返工的原因及已经验证的纠正措施。区分观察到的事实与推测的原因，检查反例，并判断问题出在已有规范未执行、流程缺少检查，还是实现本身有缺陷。只有证据显示问题曾多次发生时，才认定为重复问题。
2. 把可复用的经验写成具体动作和检查点。说明何时适用、修改前或修改中要做什么，以及报告完成前如何端到端验证原始要求。对于修改不到位的问题，指出遗漏的入口、调用方、场景或验收条件，并提出能发现该遗漏的检查。每项完成结论都应对应在最终修改上、通过受影响入口执行的检查。可行时，验证回归检查能在修复前发现原始问题，并在修复后通过。说明跳过或无法执行的检查。成功的恢复步骤或失败的尝试只有能改变下次做法时才记录。
3. 收集用户和 Agent 在开发中指出的长期规范。以用户明确要求、项目现行权威指引或相关验证结果为依据。Agent 的建议或一次成功实现不足以确立项目级规则。把尚不确定的规范作为提案，略过临时指示、原始会话记录、敏感信息及项目已通过工程手段落实的经验。结合重复观察和反例判断规则是否成立，将项目特有做法限制在其适用范围。保存前先判断，后续开发者即使遵循现有代码、测试和文档，是否仍可能重复犯错或重新调查原因。如果这些材料已能提供答案，就跳过额外记录。

## 确定位置并提交确认

- 根据问题成因选择改进方式。可机械检测的行为建议用回归测试或自动检查，可重复流程建议写入操作手册或 Skill，需要在动手前知晓的长期项目约束适合写成简短指令。已有规范未被执行时，先查明为什么会被遗漏，再决定是否需要新增规则。
- 采用最小适用范围。起草新增规则前，按语义查找等效规则。获准澄清或替换现有规则时，更新原有来源。根据当前项目证据核对旧规范，发现过时时建议在原处更新。指出无法解决的规范冲突。沿用项目已有的决策记录流程，包括项目已采用的 `agent-notes`。
- 复盘或仅调用本 Skill 时只读。用户要求保存时，可以将已验证的经验写入范围内合适的现有项目文档，同时遵守下方确认步骤。修改业务代码、测试、CI、用户级指令或 Skill 需要对应授权。
- **修改任何 `AGENTS.md` 前，必须由人二次确认。** 以下方格式中的可复制条目作为待确认草案，在该条中给出目标路径、适用范围和依据，请用户在后续回复中批准这份草案。即使用户初次直接要求更新 `AGENTS.md`，也先提交草案。等待确认期间，根目录和子目录的 `AGENTS.md` 均保持原样，工具或脚本也不得代为修改。待确认的规范不得通过其他指令文件提前生效。
- 只落实已批准的变更，并检查目标文件是否出现了与草案冲突的新改动。措辞、范围或目标位置需要实质调整时，展示更新后的草案并重新取得确认。

## 输出可直接复制的草案

默认按 **Agent 改进** 和 **项目规范** 分成两组短编号列表，同等看待两组。开头直接进入这两组。中文标题固定为「Agent 改进」和「项目规范」，其他语言对应翻译，依据使用用户的语言，已知目标文件语言时，草案沿用该语言。

- **Agent 改进**聚焦 Agent 根据当时已知信息可以做得更好的地方。优先提炼明确纠正、遗漏要求和可避免的验证缺口。区分后来新增的要求、正常的方案演进，以及当时无法预知的结果。把经验写成在明确场景下可执行的动作，必要时附检查点，建议放到最适用的工作流程或文件中。
- **项目规范**收录用户指出或项目权威资料支持的长期本地规则。最终改动中的实现细节只有具备长期约束的证据时才列入。优先沿用用户明确认可的措辞，跳过现有等效规则。拟修改 `AGENTS.md` 时给出目标路径和适用范围。

每条先用 Markdown 引用块展示可直接复制的草案，再用一句话交代依据，并标注目标文件或作用域。每条草案只展示一次。按分组和编号请用户确认已展示的草案，避免在额外的 diff 或总结中复述。内容的依据、范围或审批决定不同时拆开列。只保留少数高价值草案，某组无合格内容时写「无」。除非用户要求，省略表格、交付总结、测试总数和业务时间线。测试证据只在能支撑草案或改变可信度时引用。复盘最近会话时，按原题列出实际读过的会话，并说明覆盖限制。最后用一行说明文件是否修改、是否待确认。获准写入后重新读取相关文件，报告实际落实的内容。
